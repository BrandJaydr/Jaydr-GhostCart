# Sentinel Posture Decision — Issue #107 (GC-99-FU2)

**Date:** 2026-11-18  
**Agent:** ChatGPT (Sentinel / RANGER review)  
**Branch:** `workers/sentinels/chatgpt-107`  
**Base:** `team/sentinels`  
**Disposition:** **KEEP, but strictly gate the development CredentialsProvider to local development. Do not leave it enabled in production.**

## Executive decision

Keep the seeded CredentialsProvider as a local-development convenience because the repository deliberately creates a development tenant and user in migration `0003_rls_seed.sql`. Remove its ability to authenticate in non-development environments.

This is a posture decision only. No application code or environment files were changed in this issue.

## Evidence reviewed

- `src/lib/auth/config.ts` on `team/builders`: CredentialsProvider authorizes a static `dev-user-1` when submitted email/password equal `DEV_SEED_EMAIL` and `DEV_SEED_PASSWORD`. There is currently **no NODE_ENV guard** around this path. The tenant ID comes from `DEV_TENANT_ID`, with a hardcoded UUID fallback.
- `.env.example` on `team/builders`: documents `DEV_SEED_EMAIL`, `DEV_SEED_PASSWORD`, and `DEV_TENANT_ID=tenant_dev_001`. That tenant value is not a UUID and is inconsistent with the UUID requirement in the tenant guard.
- `src/lib/auth/tenant.ts`: `getAuthenticatedTenantId()` accepts only a UUID-shaped tenant ID and otherwise returns `null`. Therefore, a local setup that copies the example tenant value can authenticate at the NextAuth layer but then fail tenant authentication for protected API routes.
- `src/db/migrations/0003_rls_seed.sql`: seeds the development tenant with UUID `00000000-0000-0000-0000-000000000001` and a development user `dev@ghostcart.local`. This supports retaining a dev-only path, rather than deleting the provider without a replacement local login.
- `docker-compose.yml`: configures `NODE_ENV=development` and passes `NEXTAUTH_SECRET` / `NEXTAUTH_URL`, but does not currently pass `DEV_SEED_EMAIL`, `DEV_SEED_PASSWORD`, or `DEV_TENANT_ID` into the app service. The seeded login may therefore not work in the documented Compose setup unless those values are wired through.
- `src/app/(dashboard)/layout.tsx`: redirects users without a session to `/sign-in`. The CredentialsProvider is part of the sign-in route flow; gating it should preserve normal session handling.

## Risk assessment

**Primary risk: production authentication bypass via development credentials.** If the development seed email/password are configured in a non-development deployment, the current `authorize()` function will accept them and mint a session for the static development identity. The fact that the values are environment-provided does not make the path safe for production: the code does not currently restrict the provider to development mode.

**Tenant consistency risk:** the example tenant ID (`tenant_dev_001`) fails the UUID check in `getAuthenticatedTenantId()`. The migration's actual seeded UUID is `00000000-0000-0000-0000-000000000001`.

**Operational risk:** Compose does not pass the seed variables into the app container, so the documented local environment may not enable the seeded login even though the database seed exists.

## Exact follow-up change recommended (separate code PR)

1. In `src/lib/auth/config.ts`, make the dev CredentialsProvider refuse authorization unless `process.env.NODE_ENV === 'development'`. This guard must run before comparing submitted credentials. Keep production authentication dependent on a real provider, not this static user.
2. Require non-empty `DEV_SEED_EMAIL` and `DEV_SEED_PASSWORD`; do not allow two missing environment variables and two empty submitted values to compare as a successful login.
3. Require a UUID-valid `DEV_TENANT_ID` that corresponds to the seeded dev tenant. Prefer no silent arbitrary tenant fallback. If the intended fixed seeded UUID is retained as a development-only default, document it and test it explicitly.
4. Correct `.env.example` so `DEV_TENANT_ID` is `00000000-0000-0000-0000-000000000001`, matching migration 0003 and the tenant guard.
5. Wire the three dev seed variables into the Compose app service using environment interpolation from `.env`; do not hardcode a password in Compose or source.
6. Add focused tests proving: (a) matching dev credentials are rejected when NODE_ENV is production/test; (b) valid configured dev credentials succeed only in development and return the seeded UUID; (c) missing credentials or malformed tenant IDs fail closed.

## Scope and verification

- Read-only review of the files listed above and issue #107.

- No tests, typecheck, lint, build, or live authentication test run in this review-only task.

## Conclusion

**KEEP, GATED.** Retain the provider only as a local-development fixture, guard it explicitly against non-development environments, and align its tenant configuration with the seeded UUID. Implement the code changes and tests in a separate, explicitly scoped follow-up PR as required by issue #107.
